# Offline Sync Conflict — When Devices Disagree

A backend that synchronizes changes from multiple devices against shared
records, detects conflicts instead of silently overwriting data, and applies
a clear, deterministic resolution strategy wherever one is safe to apply
automatically — falling back to explicit manual resolution only where no
automatic merge is safe.

## Quick start

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

The API is now at `http://localhost:8000`. Interactive Swagger docs are at

## The problem, restated precisely

A client holds a local copy of a record. It edits fields while offline, then
reconnects and pushes those edits to the server. Meanwhile, another device
may have pushed its own edits to the same record in between. The server has
to decide, per field, whether the incoming value should win, lose, or be
merged alongside the other device's edits — without ever silently discarding
a newer change in favor of an older one, and without needlessly flagging
non-conflicting edits as conflicts.

## Design decisions

### 1. Ordering changes: a Hybrid-Logical-Clock-style timestamp, not arrival order

Network arrival order tells you nothing about *when* an edit was actually
made offline — a change made at 9:00 AM might reach the server after one made
at 9:05 AM. So every field edit carries a timestamp the **client** generates
at the moment of the edit, not a server-assigned one:

```
timestamp = (physical_time_ms, logical_counter, device_id)
```

This is a simplified Hybrid Logical Clock (HLC): `physical_time_ms` is the
device's wall clock; `logical_counter` disambiguates multiple edits made in
the same millisecond on the same device; `device_id` is the final,
deterministic tie-breaker so **two timestamps are never equal unless they are
the same event** — total ordering is guaranteed even under clock skew or
exact ties. Timestamps compare lexicographically as a tuple. A reference
client-side generator is in `app/hlc.py` (`HLCClock`) and used throughout the
tests to simulate multiple independent devices.

This is what actually answers "what happens when changes were made
independently from different versions of the same data" — the server never
has to guess which edit is newer, because the edit itself carries that
information.

### 2. Conflict resolution strategy: field-level last-write-wins (LWW)

Each record is a bag of independently-timestamped fields:

```json
{
  "title": {"value": "...", "timestamp": [1730000000000, 0, "phone"]},
  "price": {"value": 42,    "timestamp": [1730000005000, 1, "laptop"]}
}
```

On an upsert, **each field is compared independently** against the field
currently stored:

- incoming timestamp is newer → **accepted**, field is overwritten
- incoming timestamp is older → **rejected** as stale; the response tells the
  client the current server value so it can reconcile its local copy
- timestamps are identical → treated as a duplicate replay of the same event
  (safe no-op, not a conflict)

Because this happens per field rather than per record, **two devices editing
different fields of the same record never conflict** — both edits apply
cleanly. A device editing a field another device already overwrote more
recently gets that one field rejected, not the whole change. This directly
satisfies "changes that do not actually conflict should not unnecessarily be
treated as conflicts" and "preserve valid changes wherever possible."

The response's overall `status` summarizes the per-field results:

| status      | meaning                                                   |
|-------------|------------------------------------------------------------|
| `accepted`  | every field in the change applied                          |
| `rejected`  | every field in the change was stale                        |
| `merged`    | some fields applied, some were stale                       |
| `conflict`  | an edit/delete collision needs a human decision (see below)|

**Why LWW instead of CRDTs or operational transforms:** field-level LWW with
an HLC tie-breaker is the simplest strategy that is still fully deterministic
and loses no information silently — every rejection is reported back with
the value that won, so the losing client can always reconcile. CRDTs give
you automatic merging of structured types (e.g. counters, sets) but add real
complexity for marginal benefit here, since the task's data model is
arbitrary key-value fields, not a counter or a collaboratively-edited text
document. OT is the right tool for concurrent text editing, which this isn't.
LWW is the industry-standard default for this exact shape of problem (it's
what DynamoDB, Cassandra, and Riak all default to).

### 3. Version vectors: detecting staleness, separately from resolving conflicts

Each record also keeps a version vector — `{device_id: count}` — incremented
whenever that device's change actually modifies the record. A client
includes `base_version`, the version vector it last saw, with every change.
The server compares it against the record's current version vector: if any
device has advanced further than the client's `base_version` knew about, the
response sets `"stale": true`.

This is deliberately **independent of field-level conflict resolution** —
staleness is informational (it tells a client "you're about to write without
having seen everything"), while the per-field timestamp comparison is what
actually decides whether an individual field update is applied. A client can
be stale on a field it isn't touching and still have its change accepted
outright.

### 4. The one case that needs a human: edit vs. delete

Field-level LWW cannot safely resolve a collision between "edit this field"
and "delete this whole record" — there is no value to merge toward. The
server detects this specifically:

- **Delete arrives, but a field was edited after the delete's timestamp** →
  the record is marked `conflict`, the delete is *not* applied, and the
  conflicting field(s) are stored as the pending change.
- **Edit arrives for a record that's already deleted, and the edit's
  timestamp is newer than the delete** → same thing, in reverse: marked
  `conflict`, the edit is held pending.
- **Edit arrives for a deleted record, but the edit is *older* than the
  delete** → not a conflict at all — the delete wins outright, and the edit
  is rejected with `reason: "record_deleted"`.

While a record is in `conflict`, *all* further changes to it are rejected
with `conflict_pending` until it's resolved — this prevents the conflict
state itself from being silently clobbered by a third write.

Resolution is explicit, via `POST /records/{id}/resolve`:

```json
{"device_id": "phone", "resolution": "keep_deleted", "timestamp": [..., 0, "phone"]}
```

or `"resolution": "restore"`, which re-applies the pending edit and brings
the record back to `active`. This mirrors how real sync systems (e.g. Dropbox
conflicted-copy files, CouchDB's `_conflicts`) punt exactly this one
ambiguous case to the user rather than guessing.

### 5. Idempotency: duplicate and lost-response requests

Every change carries a client-generated `change_id`. Before applying
anything, the server checks `(device_id, change_id)` against a
`processed_changes` table; if it's seen that pair before, it returns the
**exact cached response** without reapplying the change. This handles the
"client sends chunk → server applies it → response is lost → client retries"
scenario safely: the retry is a no-op that still returns a successful
response, rather than double-applying or erroring.

### 6. Concurrency: per-record locking

Multiple sync requests touching the same record are serialized with an
in-process lock keyed by `record_id` (`app/locks.py`), so read-modify-write
on a record's fields/version/status is atomic. Different records are never
blocked by each other. This is the right scope for a single-process
deployment; a multi-process deployment would need the lock to move into the
database (e.g. `SELECT ... FOR UPDATE` on Postgres, or a Redis-backed lock) —
noted here as a deliberate simplification, not an oversight.

### 7. Out-of-order and duplicate-looking requests

Because ordering is decided by the HLC timestamp embedded in each field
change — not by when the HTTP request arrives — changes that arrive
out of order resolve identically to changes that arrive in order. There's no
separate "reordering" logic because the comparison is timestamp-based from
the start.

## API

### `POST /sync`

```json
{
  "device_id": "phone",
  "changes": [
    {
      "change_id": "client-generated-uuid",
      "record_id": "note-1",
      "operation": "upsert",
      "base_version": {"phone": 2, "laptop": 1},
      "fields": {
        "title": {"value": "Grocery list", "timestamp": [1730000000000, 0, "phone"]}
      }
    },
    {
      "change_id": "another-uuid",
      "record_id": "note-2",
      "operation": "delete",
      "base_version": {"phone": 1},
      "timestamp": [1730000000500, 0, "phone"]
    }
  ]
}
```

Response:

```json
{
  "device_id": "phone",
  "results": [
    {
      "change_id": "client-generated-uuid",
      "record_id": "note-1",
      "status": "accepted",
      "stale": false,
      "was_new_record": false,
      "server_version": {"phone": 3, "laptop": 1},
      "fields": {"title": {"status": "accepted"}},
      "record_status": "active"
    }
  ]
}
```

### `GET /records` — list all records (debugging/demo)

### `GET /records/{id}` — current state of one record

### `GET /records/{id}/history` — every applied/rejected change, in order (bonus: change history)

### `POST /records/{id}/resolve` — resolve a pending edit-vs-delete conflict

```json
{"device_id": "phone", "resolution": "restore", "timestamp": [1730000100000, 0, "phone"]}
```

## Testing the scenarios from the brief

`tests/test_sync.py` has one test per required behavior:

- newer change accepted, older change rejected with the current value returned
- two devices editing *different* fields of the same record both succeed (no false conflict)
- a change that's partly accepted and partly rejected reports `merged`
- the exact same `change_id` sent twice is a no-op the second time (lost-response retry)
- a stale `base_version` is reported even when the field-level write still succeeds
- delete-after-concurrent-edit and edit-after-concurrent-delete both require explicit `/resolve`
- a record stuck in `conflict` rejects further writes until resolved
- five concurrent requests against the same record all apply correctly (locking)

Run `pytest tests/ -v` to see all pass.

## Known limitations / explicitly out of scope

- The per-record lock is in-process, so this doesn't horizontally scale
  across multiple server instances without moving locking into the database.
- There's no authentication — any `device_id` can write to any record. A
  real deployment would authenticate the device and probably scope records
  to an owner.
- Field values are stored and compared opaquely (as JSON) — there's no
  type-aware merging (e.g. numeric fields don't support additive/CRDT-style
  merging, only LWW). This was a deliberate scope decision; see "why LWW"
  above.
